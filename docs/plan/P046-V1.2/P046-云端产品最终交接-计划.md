## 3. Product Goal / Target Users / Problem / Core Value

- **Product Goal**：朋友突然邀请打麻将时，用户可快速选具体地方玩法，看到最关键的上桌规则；通过真正麻将图案理解“能不能胡、为什么、差什么”及例外。
- **Target Users**：不会打、玩过两三次忘记规则、临时玩别的地区麻将的人。
- **Problem**：网上规则互相矛盾；熟人解释太专业；“眼”和“花”关系难懂；看文字不能直观看手牌。
- **Core Value**：**牌面先行，一句人话解释，明确玩法和判断前提**；不是线上打麻将/考试/计分工具。

## 5. Functional Scope（FR，拟入 ORCA 正式模板）

**P0**：
- `FR-01` 按地区选具体玩法；同一地玩法多选，展示版本与来源。
- `FR-02` C 型首页两个大入口：**地区**/**问题**；无底部 Tab；设置右上角，首页搜索。
- `FR-03` 每个基础胡牌/番种术语都有**真实麻将牌面图片**，且展示牌张分组、缺的牌/条件、是否已满14张。
- `FR-04` “能胡 / 不能胡 / 未满足额外条件 / 依据不足”的结论四态，按具体玩法和上下文判定；13张等待牌和14张不完整分开解释。
- `FR-05` 眼/将、碰、杠、吃、花、番、缺门、自摸、点炮等术语用人话 + 图示；地方争议词保留限定提示。
- `FR-06` **3分钟速看**：按玩法直达，无课程、练习题或强制登录。
- `FR-07` 带核实等级、来源、时间与争议说明的规则库及版本记录；不把SEO伪“官网”当标准。
- `FR-08` 首批已核实规则和麻将图片**离线可用**；无网络仍可读，来源链接联网时可点。
- `FR-09` 中文/英文正式品牌名、Launcher 自适应图标、单色图标和 Android 系统启动品牌资源，来自本交接包，不得自行发明。

**非阻塞 P1**：`FR-10` 两版本规则差异对比；`FR-11` 最近查看/模糊搜索；`FR-12` 非主流地区追加内容的扩展接口。

**全局 APP 默认（按 ORCA 现行规范原样继承）**：`FR-13` LIGHT / DARK / SYSTEM，默认 SYSTEM，全页面一致；`FR-14` zh-CN + en，FOLLOW_SYSTEM 默认，不支持语言回退 zh-CN；`FR-15` 设置保存、切换不清状态、未来增语言只添资源/必要适配；`FR-16` 复用成熟官方框架，不自造第二套导航/国际化/主题工具。

**明确不做**：麻将线上对战、AI/拍照自动判牌、复杂算番/算钱、赌注/下注、积分排行榜、练习题/考试、小测验、大型麻将历史百科、强制启动引导页。

## 6. User Flow（UX 真源）

- UF-01：首页 → 地区（海南/四川/重庆/广东）→ **具体玩法名字** → 规则简介 → 对照牌面 → 3分钟速看。
- UF-02：首页 → 问题「什么是眼」→ 对比有眼/无眼真实牌面 → 一句原因 → 返回。
- UF-03：首页 → 「为什么不能胡」→ 区分13张/14张与来源 → 手牌结构/地域条件两级判定 → 说明缺牌或缺资格。
- UF-04：海南页 → 「二五八眼」与「对应座位花」两个示例，**花牌另放**，不把花和眼合并。
- UF-05：四川页 → 结构看似完整但有三门花色 → 高亮违背定缺的花色；变体项有开关。
- UF-06：广东推倒胡页 → 同一完整结构，最后一张来源不同（自摸/普通点炮）显示不同结果。
- UF-07：进入具体玩法的「对比」→ 选择第二个明确规则版本 → 明确差异和证据等级。
- UF-08：设置 → 浅/深/系统 + 简中/英/系统 → 返回仍保持所在规则和浏览状态。

- `AC-28｜关键：是｜关联 UF-08`：Android 自适应图标前景/背景/monochrome 可安装；系统 splash 随主题呈现，不新增假等待页面；实际设备录屏。

**关键 AC 集合输入草案**：AC-01～AC-19、AC-22～AC-28；AC-20/21 可以非阻塞。沿用 ORCA 正式要求核对 FR/AC/UX/任务/QA 关系，**禁止**把云端测试结果登记成 Android QA PASS。

## 9. 实际技术与平台原则

- **Android 原生优先**：既有本地工作环境支持安卓开发；可用 Jetpack Compose/Material 3、官方资源语言方案，Runtime / Compose BOM 由项目实际复用审查确定。MagicPath React 原型不是现成的 Compose APK。
- 规则数据：静态离线 JSON + 明确玩法版本/证据/上下文；不引入线上对战或牌局 API。`rules/rule-profiles.json` 和 `examples/visual-examples.json` 为 Phase 1 输入资产，开发者可在保持语义/ID稳定前提下正规化。
- 图案：本包 PNG 可用于真实牌面; 牌图与上下文优先展示。扩展图资必要时制作自有资源，避免授权不明第三方图库。
- 声明：这不是博彩产品；不做金额计算或实际下注。
- 主题/多语言：默认继承现有 `app-theme-i18n.md`，不删减关键 AC；Android `SplashScreen`（真实系统界面）不等于一张长时间显示的插画。

## 10. 阶段与审查职责（实现连续推进而不取消 ORCA 必要边界）

### Phase 1：已有产品决策 → 正式原型

- 读取云端品牌/规则/牌面/UX 合同；本地 Planner 核对模板一致性、Research Reviewer 验证证据等级和资料转化、设计者正式可点击原型化、UX Contract 与 QA 可测试化。
- 本阶段不新开 A/B/C 让用户重复挑方向（C 已定），也不让本地模型挑中文名与 Logo；如现行 ORCA 模板必须记录历史 A/B/C，可用既有云端决策和参考方案作为材料，**不能伪造曾经有新三版 Human1审批证据**。
- **一次 Human 2**：给用户正式完整可交互原型；用户只需一次说“原型确认，通过，第二阶段，开发”。无需问零碎颜色、文案、卡片布局。真实碰到需要新的不可撤销授权等以既有规则汇总。

### Phase 2：固定产品 → 自动完成所有 TASK

- 获用户现有明确开发授权后执行正式冻结基线/SDD/TASK，Builder–Reviewer–QA–Supervisor 闭环连续推进至全部关键 AC 通过。失败回派原链/按原有升阶策略处理，不以普通 bug 多次打断用户。
- 仅报告真实阻塞、高风险外部授权、现行必要 Human Gate、以及**首次发布最终签收**。不悄悄改变正式 Gate 或绕过用户授权。

### Risk / DoD

- P0 产品内容风险已通过**有证据内容入库，查不明白内容不出肯定结论**解决；牌桌真实自定义规则不可通过网络穷尽，产品上应以“具体版本/先问桌规”设计处理。
- 16例原型检查：全部有对应牌图；核心例子经排列/枚举结构数学自检；具体地区附加条件逐条人工证据审查。
- 项目首次发布类型：`首次发布`，需要正常的用户最终签收。
- ORCA `Readiness Score`/`PLAN_GATE`/`DEV_BASELINE`/正式 Design Freeze **由本地真实流程产生，不提前填 PASS**；此次交付不代表本地项目代码已自动修改。
